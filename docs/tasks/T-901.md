# T-901 — Monthly seller invoice for Manual orders above the free quota

## Goal
After Gate D, on the 1st of each month every non-exempt seller with more than 50 confirmed Manual orders last month gets an invoice for Rp1.000 per order above 50, minus credits for refunds caused by the seller or by a system error, by WhatsApp and on the dashboard.

## Context
- ADR 0006, including the **amendment of 2026-11-12** (refund credits, unpaid invoices, issuer). T-407 (usage data).
- ADR 0002 is unaffected: the invoice is DropKilat's own fee, paid by the seller. No buyer money is involved.
- `docs/app-flow.md` §5 (the three transitions into `refund_pending`), `docs/backend.md` §3–4 and §8.
- **Blocked until:** Gate D passed **and** Nur has done the tax/legal check (invoice format; PPN if DropKilat is PKP) **and** Nur has provided the issuer configuration.

## Scope
- In:
  - migration `00000N_invoices`: `invoices`, `invoice_lines`, `billing_credits`, `orders.refund_cause`;
  - `refund_cause` set on every transition into `refund_pending`; `POST /seller/orders/{id}/cancel` takes a required `cause` (`seller` | `buyer_request`); owner action to set `system_error`;
  - `invoicer` worker (issue, credits, reminders);
  - invoice page and printable view for the seller, with the issuer snapshot;
  - `wa.seller_invoice`, `wa.seller_invoice_reminder`;
  - owner screen: list issued/overdue invoices, mark paid, void, set `system_error` on a refunded order;
  - overdue block on drop create and publish behind `DK_BILLING_ENFORCE_OVERDUE`;
  - config: `DK_FEATURE_BILLING`, `DK_BILLING_ENFORCE_OVERDUE`, `DK_INVOICE_ISSUER_NAME`, `DK_INVOICE_BANK_NAME`, `DK_INVOICE_BANK_ACCOUNT`, `DK_INVOICE_BANK_HOLDER` (+ `.env.example` with empty values).
- Out: automatic collection, card payments, buyer-side cancel after `paid`, late fees or interest, partial payments.

## Interfaces
```sql
ALTER TABLE orders ADD COLUMN refund_cause text
  CHECK (refund_cause IN ('seller', 'buyer_request', 'system_error', 'dispute', 'late_payment'));
-- set exactly when status becomes refund_pending; NULL before T-901 (pilot, never billed)

CREATE TABLE invoices (
  id           uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  seller_id    uuid NOT NULL REFERENCES sellers(id),
  number       text NOT NULL UNIQUE,             -- DK-INV-YYYYMM-<seq>
  month        date NOT NULL,                    -- first day of the billed month (WIB)
  charge_qty   integer NOT NULL CHECK (charge_qty >= 0),   -- confirmed − 50, frozen at issue
  amount       bigint NOT NULL CHECK (amount >= 0),        -- sum of lines
  status       text NOT NULL CHECK (status IN ('issued', 'paid', 'void')),
  issuer_enc   bytea NOT NULL,                   -- AES-GCM JSON snapshot: issuer name, bank name, account, holder
  issued_at    timestamptz NOT NULL,
  due_at       timestamptz NOT NULL,             -- 10th of the issue month, 23:59:59 WIB
  reminded_at  timestamptz[] NOT NULL DEFAULT '{}',
  paid_at      timestamptz, voided_at timestamptz,
  UNIQUE (seller_id, month));
CREATE TABLE invoice_lines (
  invoice_id   uuid NOT NULL REFERENCES invoices(id),
  seller_id    uuid NOT NULL REFERENCES sellers(id),
  kind         text NOT NULL CHECK (kind IN ('charge', 'credit')),
  description  text NOT NULL,
  qty          integer NOT NULL CHECK (qty > 0),
  unit_price   bigint NOT NULL,                  -- +1000 charge, −1000 credit
  amount       bigint NOT NULL CHECK (amount = qty * unit_price),
  CHECK ((kind = 'charge') = (unit_price > 0)));
CREATE TABLE billing_credits (
  order_id           uuid PRIMARY KEY REFERENCES orders(id),   -- one credit per order, ever
  seller_id          uuid NOT NULL REFERENCES sellers(id),
  confirmed_month    date NOT NULL,
  amount             bigint NOT NULL CHECK (amount = 1000),
  created_at         timestamptz NOT NULL,
  applied_invoice_id uuid REFERENCES invoices(id));
-- tenant RLS on all three; audit_log on issue, credit, paid, void, system_error
```

Invoicer run for month M (one `system` transaction per seller, `$now` from `clock.Clock`):
1. Skip exempt sellers and sellers with `DK_FEATURE_BILLING=false`.
2. Create missing credits: for every earlier or current month K with `charge_qty_K > 0`, take orders confirmed in K with `refund_cause IN ('seller','system_error','dispute')`, ordered by refund time; insert credits until the credits for K equal min(`charge_qty_K`, that count). `ON CONFLICT (order_id) DO NOTHING`. For K = M, use the `charge_qty` being issued now.
3. `charge_qty = max(0, confirmed_M − 50)`. Apply unapplied credits oldest first, at most `charge_qty` of them.
4. If `charge_qty = 0`, issue no invoice; any credits stay unapplied for the next one.
5. Lines: one `charge` line, one `credit` line per confirmed month credited. `amount = Σ lines ≥ 0`.

## Acceptance criteria
1. Running the invoicer twice for the same month creates one invoice per seller (`UNIQUE (seller_id, month)`) and no duplicate credits.
2. Charge = (confirmed − 50) × Rp1.000 for non-exempt sellers. A seller at or below 50 gets no invoice. Exempt sellers get none.
3. Refund rule (ADR 0006 amendment), each a named test:
   - order confirmed in M, refunded with cause `seller` in M+1 → counted on M's invoice, credit −Rp1.000 on M+1's invoice;
   - same with cause `buyer_request` → no credit;
   - cause `system_error` set by the owner → credit; a seller cannot set `system_error` (403);
   - refunded in M before M's invoice is issued → credit on M's own invoice;
   - order confirmed in a month where the seller stayed ≤ 50 → no credit (the fee was never billed);
   - credits exceeding the next invoice's charges carry over; no invoice amount is negative;
   - the same order never yields two credits.
4. Reminders by WA at `due_at` and `due_at + 7 days`, each sent once (dedupe on `reminded_at`).
5. With `DK_BILLING_ENFORCE_OVERDUE=true` and an `issued` invoice past `due_at + 14 days`, `POST /seller/drops` and `/publish` return `invoice-overdue` (403) with copy "Ada tagihan DropKilat yang belum dibayar lebih dari 14 hari. Bayar tagihan untuk membuat drop baru." Live and scheduled drops keep running; claims, proofs, confirms and shipping work. Marking the invoice paid or void lifts the block at once. With the switch `false`, nothing is blocked.
6. With `DK_FEATURE_BILLING=true`, startup fails if any `DK_INVOICE_*` variable is empty (error names the variable, not the value). The bank account never appears in logs; a log-capture test checks it.
7. All amounts `int64` rupiah; invoice and lines reconcile in a SQL test (`invoices.amount = Σ invoice_lines.amount`, credits applied = credit lines).
8. An issued invoice keeps its issuer snapshot after the config changes.

## Test expectations
- Integration with the fake clock across month boundaries (M, M+1, M+2) and the WIB/UTC edge at 00:00 WIB on the 1st.
- Worker idempotency; RLS (seller A cannot read seller B's invoices or credits).
- Handler tests for `cause` validation and the `invoice-overdue` gate on both switch values.

## Risks and notes
- Real money and tax: escalate any change in amounts or rules to Nur.
- Issuer data is Nur's personal data: only in env/secret, encrypted at rest in `issuer_enc`, never in fixtures or logs. Tests use dummy values.
- The cancel endpoint may already exist from P4; this card adds the required `cause` and keeps the old behavior otherwise.
